实现线上手写作业自由：手写模拟网站开发记录

发表于 2026-11-15 分类于 项目实战
从本地脚本到线上网站——上传题目、AI 解答、导出手写版 PDF，直接传到畅课交作业，包含技术栈、项目结构与渲染思路

实现线上手写作业自由：手写模拟网站开发记录

📖 前言：为什么想做这个

先说动机，很简单：天下苦手写作业久矣。

现在交作业基本都走线上了。像我们用的畅课，就要拍照上传手写的作业。

可是每次手写都很麻烦。说不上多喜欢数学，但每次数学作业不会写就搜 AI，然后把 AI 的答案抄到作业本上，这个真的很麻烦哎！作业这么多，一直抄真的好累啊！

我就有个想法：能不能做一个网站，只要上传题目，就直接调用 AI 解答，再把答案变成手写的形式，导出成 PDF 或者图片——这样在畅课上直接上传就行。这不就实现线上作业自由了吗？能省下好多时间。

而且我写字本来就不算快，几页作业写下来手是真的酸。更别说证明题，草稿上改来改去，最后交上去的那版跟草稿早就不是一回事了。

所以就有了这个想法：不只是把答案”抄”成手写，而是让整个过程自动化——上传题目，AI 给出解答，最后我拿到一份看起来像真人手写的 PDF。

最开始它只是我电脑上的一个本地小工具（D:\Program Files\手写模拟\ 里那个 exe），用真实的作业本照片当底图，把文字渲染上去。后来觉得每次都要在本地跑太麻烦，干脆搬到了服务器上，做成了网站：math.xiaoxiaoyu123.xyz，打开就能用。

这篇就记录一下它现在的样子、技术栈，还有渲染大概是怎么做的。不讲太深，踩过的坑单独写。

👀 它现在长什么样

网站很朴素，就三个标签页：

  • 写作业：左边选纸张、字体、潦草度；中间输入文本，也可以让 AI 直接解题；右边实时预览手写效果，满意了导出 PDF / PNG
  • 字体工坊：打印模板 → 手写填格 → 拍照上传 → 生成属于你自己的手写字体
  • 公告：关于这个工具的一些说明

写作业页的核心是中间那个输入框。它不是普通的文本输入——里面有一套自己的数学记号语法，比如：

写法 渲染成
fr{1}{3} 上下结构的分数
∫[0,1] 带上下限的积分号
√(x+1) 根号
sb{a}{n} 下标
lim{x→0} 极限（过程写在正下方）
Σ[i=1,n] 求和号
mat(1 2; 3 4) 矩阵（含增广虚线、行变换箭头标注）

输入的时候页面会做记号体检，有写错的地方直接标出来，不用等渲染失败才发现。

另外还有几个顺手加的功能：

  • 📷 拍题：题目拍照，AI 抄成文字
  • 📄 导入：Word / 文字版 PDF 直接抽文本，不消耗 AI 次数；扫描版 PDF 可以逐页让 AI 识别
  • 🤖 AI 解题：按本站记号规范写答案，流式输出，能随时停止

这些 AI 功能用的是站点内置的 Key，每人每天有次数限制，不用自己配。

🧱 技术栈

技术选型没什么花哨的，都是自己熟悉、能跑在 2 核 2G 小服务器上的东西：

层 用的什么 说明
前端 Vue 3 + Vite 单页应用，三个 tab 切换，没上路由
样式 原生 CSS + CSS 变量 一套粉白主题，变量化管理颜色和圆角
数学排版 KaTeX 只用于 AI 原文的公式预览，不参与导出
后端 FastAPI + uvicorn 接口不多，主要是渲染、导出、字体工坊、AI 转发
渲染 handright 8.2.0 + Pillow 手写模拟的核心引擎
字体处理 fonttools + scikit-image 字体工坊的切割、轮廓提取、TTF 组装
文档解析 pypdf + python-docx 导入 Word / PDF
部署 阿里云 2C2G + 1Panel + OpenResty 小水管，够用

为什么不用更”现代”的东西？因为整个应用其实就一个页面，状态也不复杂，Vue 3 的响应式加上一个 store 就够了。后端渲染是 CPU 密集型，单 worker 队列反而更好控制——反正 2 核的机器也并行不了几个渲染任务。

📁 项目结构

分成了前后端两个仓库，前端公开、后端私有。

几个关键设计：

  • 会话模型：左侧历史列表里每一条就是一个”任务”，题目、答案、预览、导出链接都跟着会话走，切来切去不丢
  • 用户资产隔离：不上账号系统，每个浏览器生成一个 client_id，上传的字体和纸张就绑在这个 id 下，别人看不到
  • 内置素材：蓝本1、蓝本2、红纸这些真实作业本照片放在后端，前端按需拿

✍️ 渲染是怎么做的

这部分是核心，但原理其实不复杂，简单说一下。

手写感从哪来

直接用系统字体渲染出来的字，整齐得像打印的，一眼假。

handright 这个库的思路是：把每个字单独画到画布上，但每个字的位置、大小、角度都做随机扰动——往左偏一点、往上飘一点、轻微旋转、字号忽大忽小，行与行之间还有轻微的基线漂移。

单看每个字都很规整，但整体看过去就有了真人写字那种”不完美”的呼吸感。潦草度三档（工整 / 正常 / 潦草）本质上就是调这组扰动参数的强度。

数学排版是自己补的

handright 只管”把字画上去”，它不认识分数、积分、矩阵这些结构。

所以我在它上面加了一层自己的记号解析：

  1. 先把文本里的 fr{1}{3}、∫[0,1] 这类记号解析出来，切成普通文字段和”公式段”
  2. 普通文字交给 handright 正常排版
  3. 公式段自己算位置：分数要分成上下两半、横线画在中间；积分的上下限要画在符号右侧的上下角；极限的过程要画在 lim 正下方；矩阵要按行列排布、还要画增广虚线和行变换箭头

这一层是最花时间的，因为要跟手写引擎的随机扰动配合——分数盒的位置偏了会顶进上一行，矩阵的标注写得太长会盖到旁边的矩阵上。这些都是靠一遍遍看渲染结果调出来的。

上标用私有区字形解决

数学里 x^2、e^(-jωt) 这种上标很常见，但手写字体里没有现成的上标字形。

解决办法是用 PUA（Unicode 私有区）字符：make_sup.py 把 ^ 记法转换成私有区的”真上标”字符，同时给字体补上这些字形的缩小版。渲染时看到的就是真正的小号字，跟在字右上角，而不是用 ^ 凑合。

纸张是真实照片

底图不是画出来的横线，是真实作业本拍的照片——蓝本、红格纸，连纸张的纹理和印刷线的深浅都在。

每种纸的行距、页边距、字体大小都是实测出来的参数，存在后端。所以渲染出来的字恰好落在横线上，不会飘。

预览和导出的分工

  • 预览：只渲染当前一页，带 LRU 缓存。之前预览慢，主要慢在图片编码——一张纸的 PNG 有两三 MB。后来把预览图缩到 1100px 宽、改用 WebP，一页降到几十 KB，快了一个数量级
  • 导出：走后台任务队列，单 worker 一张一张渲染，前端轮询进度。导出的是全尺寸原图，PDF 里每页都是高清的

🔧 踩过的坑

挑几个印象深的。

坑一：分数盒会顶进上一行

分数是上下结构，一开始按”横线居中”的直觉来排，结果分子稍微高一点就压到上一行的字。

后来发现视觉上人写分数是上紧下松的——横线上方留给分子、下方留给分母，比例不是 1:1。按这个调完才自然。

坑二：矩阵的行变换标注会越界

高代题里 r2-2r1 这种行变换要写在矩阵之间的箭头上，一开始标注写太长，直接盖住了旁边的矩阵。

最后的处理是：标注按行拆开、字号缩小、箭头位置根据两个矩阵的实际间距动态算，超长就换行。

坑三：切个标签页，历史全没了

这个 bug 藏了很久。表现是：从写作业切到字体工坊，再切回来，左侧历史列表空了。

查下来是持久化的逻辑写岔了——保存时会主动剥掉预览图字段（因为图太大），但读取时又要求这个字段存在，于是全部记录被当成无效数据过滤掉了。

属于典型的”两处代码各自都合理，凑一起就不对”。修完之后切来切去历史都在了。

坑四：AI 解题状态会串台

一个会话正在解题，新建一个题目，新会话的工具栏也显示”正在解题… 27s”，还带个停止按钮——点下去停的是别人的请求。

原因是那个”正在解题”的状态是全局的，但显示逻辑没判断”是不是当前这个会话发起的”。加一个会话 id 标记就解决了。

🚀 部署与开源

线上跑在一台阿里云 2 核 2G 的机器上，1Panel 面板管理，OpenResty 做反代。机器很小，所以渲染的并发控制做得比较保守——预览有缓存和限流，导出是单 worker 排队，避免几个请求把 CPU 打满。

代码方面：

  • 前端仓库公开：handwritten-simulation-front-end
  • 后端仓库私有（里面有 Key 和服务器相关配置）

写在最后：做这个项目最大的感受是，很多”麻烦事”其实只是没人把它自动化。拍照交作业这件事，每个人都在忍受，但忍久了就当成理所当然了。真正动手做一个工具，才发现大部分环节都可以交给代码——包括那些看起来非手动不可的部分，比如”写”。

总之，以后的线上手写作业，我就一直用它了！
