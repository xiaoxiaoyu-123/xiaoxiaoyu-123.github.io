# 棉花糖今天吃啥

## 前言
小程序v1.0.2版本早于5.16号正式发布在微信小程序上了，由于界面较简便+功能过少，打算六月份中下旬优化小程序后再重新写一篇博客记录。拖着拖着到了现在8.20才写这篇博客记录。在学校的时候7.20开始重构优化项目，本想着回家前7.24前把这个小程序重构完，然而事与愿违，一托再托，回家后8.6才开始正式继续重构项目，这次前端从微信原生开发框架迁移为uniapp框架，后端从node.js（express）迁移为spring-boot框架，数据库从supabase迁移至MySQL。整个项目重构过程90%以上是用Claude Code写的了，特别是后端跟数据库完全是用Claude Code写的。运维方面，通过1panel运维管理面板部署了spring boot的后端服务。已于8.11日在微信小程序管理后台上正式发布了前前后后修改改改后的V2.0.5版本，现可正常在微信上使用。

## 为什么要把好好的小程序拆了重来

v1.0.2 其实能正常用：抽签、转盘、固定菜品，解决"今天中午吃什么"这个世纪难题基本够用了。但它实在**太简陋**了——界面是原生组件拼的，功能就那几个 tab，后端还是个 node.js（express）+ Supabase 的玩具组合。

本来想着六月中下旬抽个周末优化一下，结果一拖就是两个多月。七月二十号在学校的时候终于开了个头，当时信心满满打算回家前（7.24）就把重构做完，**结果又是事与愿违**——学校一堆事，回到家又躺了几天，真正坐下来开始写已经是 8.6 的事了。人啊，永远不要给"过几天就能做完"的项目立 flag。

## 技术栈大换血

| | 旧 | 新 |
|---|---|---|
| 前端 | 微信原生 | uni-app（Vue3） |
| 后端 | node.js（express） | Spring Boot 3 + MyBatis |
| 数据库 | Supabase | MySQL |
| 部署 | 无 | 1Panel 容器化 |

**前端为什么换 uni-app**：以后要是想上别的平台（抖音、支付宝啥的），一套代码直接打包过去；而且 Vue3 的组件化写起来比原生舒服太多了。最关键的是对微信发布流程零影响——AppID、域名、审核都不变，该咋发布还咋发布。

**后端为什么换 Spring Boot**：说实话是被 express 的异步回调折磨过，加上自己正在学的学习管理系统就是这套三层架构（Controller→Service→Mapper），正好把它的 `Result<T>` 返回风格也复用过来，写起来顺手。

**数据库为什么换 MySQL**：Supabase 免费层 + 行级安全策略（RLS）那套，对个人项目来说太重了，查个东西还绕。换成 MySQL 自己建表、自己写 SQL，清爽。

## 后端：100% Claude Code 写的

这大概是整个重构里最"夸张"的部分——我用 Claude Code 开了 **9 个并行子代理**，一次性把后端整个搭了出来：

- 48 个 Java 源文件
- 5 个 Controller、22 个接口
- 3 张表的 DDL（user / dish_history / custom_dish，后来又加了 feedback）

数据库迁移也是它干的：把 Supabase 的 PostgreSQL 表结构翻译成 MySQL 语法，废弃 RLS，改成后端业务逻辑鉴权。我基本只负责"提需求 → 验收 → 说哪里不对重来"。那段时间，我更像产品经理。

## 前端迁移的坑（能写一大篇）

### 编译阶段
- `manifest.json` 忘了加 `"vueVersion": "3"`，编译一直报错，折腾了半天
- `@dcloudio` 的 alpha 版本和 HBuilderX 内置版对不上，`uni` 直接不是内部命令
- 生命周期 `onShow/onLaunch` 要从 `@dcloudio/uni-app` 导入，而不是从 `vue`

### 九宫格菜品图片——最磨人的一个 bug
微信的 canvas 2D 在开发者工具里报 `nodeId` 错误，真机上又加载不了 HTTPS 网络图片。为了这几张菜品图，我试了 `getImageInfo`、`downloadFile`、隐藏 `<image>` 拿 path……**全都不行**。一度怀疑人生，甚至想把图片去掉算了。

最后绕过了 canvas 本身：改用微信原生的 **cover-image 组件覆盖在 canvas 上层** 来显示菜品图。代价是弹窗又被 cover-image 挡住（原生组件层级高），于是弹窗也改成了 cover-view。一环套一环，但总算是能看了。

### 真机和开发者工具总是不一样
这类小程序开发的经典痛点：开发者工具里好好的，真机上一塌糊涂；或者反过来。这个项目里至少碰到三次——颜色渲染、图片加载、弹窗层级，全是"工具里没毛病，真机就翻车"。最后只能一遍遍"传上去 → 预览 → 看效果 → 改"，非常费人。

## 上云：1Panel 部署

后端部署用的是 **1Panel** 运维面板：

- 8080 端口被占 → 改用 8081
- MySQL8 认证插件问题 → 改 `mysql_native_password`
- Nginx 反代 `/api`、`/static`、`/uploads`
- 头像上传：微信的 `wxfile://` 临时路径**只有本机能看**，别人的头像永远是裂图 → 改成先上传到后端 `uploads/avatars/` 存成永久 URL，所有人都能看

## 数据同步：最折磨人的一环

小程序的抽选是**本地优先、云端兜底**的架构：

1. 抽选先写本地，异步推云端，成功后给这条记录打 `synced` 标记
2. 启动时把没同步上的记录自动补推（重试队列）
3. 这样断网也能抽选，联网自动补上

这套架构本身没毛病，但中间踩了一个巨坑：**storage key 不一致**——登录时写的是 `what-eat_user_id`，api 层读的却是 `user_id`（恒为 null），导致云端同步**全部静默失败**，本地数据永远比云端多，统计页和排行榜怎么都对不上。

8.8 那天终于把这个数据一致性问题彻底收拾干净：
- 统计页（TOP5 / 来源占比 / 本月打卡 / 月度趋势）、我的页、排行榜**统一改读后端**，本地只当离线兜底
- 启动时始终补推未同步记录，不再"标记成已同步就丢掉"
- 请求遇到 401（后端重启后 token 失效）自动重新登录重试

## 安全加固：原来小程序也有这么多漏洞

做安全审计之前，我以为个人小程序没人看、不会有啥问题。结果一查 `SECURITY.md`，列了一大串：

- 🔴 严重：所有接口无身份鉴权（能枚举 userId 篡改他人数据、刷榜、看别人隐私）、无鉴权文件上传
- 🟠 高危：管理后台密码无限试（暴力破解）、CORS 全开、错误信息直接甩给客户端
- 🟡 中危：无限流、管理后台 N+1 全量加载、参数不校验（空 code 直接 500）

然后一个一个修：
- 登录签发 **token**，加 `AuthInterceptor` 拦截器，接口不再信任 URL 里的 userId（根治越权）
- 上传接口加鉴权 + 图片类型白名单 + 2MB 上限
- 管理后台**连续输错 5 次锁 15 分钟**，多设备 token 互不顶掉
- CORS 收紧到固定来源
- 全局异常处理器，错误信息不再泄露内部细节
- 参数校验：空 code、非法月份、超长昵称/菜名，全部返回友好提示而不是 500

有一说一，这个小程序大概也没几个人用，但既然是自己从零写到上线的后端，还是想把它弄得像样一点。

## 关于 Claude Code 的碎碎念

整个项目重构，**90% 以上的代码是 Claude Code 写的**，特别是后端和数据库，几乎是我"描述需求 + 验收"就完成了。

这种工作方式挺奇妙的：以前写代码是被一个 bug 卡一晚上，现在是**被一个描述不清楚的需求卡一晚上**——因为得先想清楚"我到底想要什么效果"，剩下的交给它写。当然它也不是万能的：

- 上下文有上限，项目大了会话会**超限中断**，只能开新会话，之前的"记忆"就没了
- 微信 canvas 这种平台的坑，它和我一样会反复试错
- 有时候要来回掰扯很多轮，它才能理解我的真实意图

但整体结论很明确：**一个人 + Claude Code，是真的能把一个小程序从零做到上线发布。**

## 结语

从 v1.0.2 到 V2.0.5，前后折腾了近一个月（集中冲刺也就两三天，剩下的全是碎片时间），换了三套技术栈，踩了无数个坑，终于在 8.11 把 V2.0.5 发布到了微信小程序上。

现在自己每天中午点开它，抽个签决定吃什么——偶尔抽到不好吃的，还会默默怪它。但这大概就是这个小程序的意义：**它不一定能帮你决定人生大事，但能帮你决定今天中午吃什么。**

棉花糖今天吃啥，就这么继续吃下去吧。
