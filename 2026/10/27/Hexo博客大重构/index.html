✨ 我的 Hexo 博客大重构

📖 前言：起因是一次「惨不忍睹」的全面扫描

这个博客搭起来一年了，27 篇文章，平时只顾着写，从来没回头检查过「房子本身」。前几天我让 AI 给项目做了一次全面体检，报告出来我人都麻了：

  • 最新的一篇文章压根没部署上线，线上还停在 9 月的版本
  • 整个项目不是 git 仓库——27 篇文章、所有配置文件，误删一个就永远没了
  • 封面图一张 1.8MB，访客打开首页约等于下载十几 MB 的图片
  • 看板娘的配置文件里写了三遍 Live2d，还互相打架

行吧，是时候大修了。这篇文章记录一下这次从头到尾的重构：干了什么、踩了哪些坑、最后长什么样。全程 AI 打下手，一个人干出了一个小团队的活。

🧹 第一章：地基治理——先把房子扶正

重构第一原则：别急着装修，先把危房扶正。

图片瘦身是最疼的一项。11 张封面全是 1.8MB 左右的大 PNG，用脚本批量转成 JPG（质量 82），单张直接降到 200KB 出头——视觉上看不出区别，体积砍到十分之一。整个 source/img 从 33MB 瘦到 15MB。

版本控制是第二疼的：赶紧 git init，先把改造前的原状提交了一份当「后悔药」，之后每做一项独立提交一条，随时可以回滚。

然后是修修补补：favicon、归档页横幅这些配置里引用但根本不存在的图片，用现有素材裁一裁补齐；顺手修了三篇文章里的坏图链接（有的少写 .png 后缀，有的图片文件早就丢了）。

🎨 第二章：封面流水线——从「临时工」到「自家人」

原来的封面是用某云的文生图 API 生成的，效果我一直不太满意，原因看完代码才明白：API 只吃文字描述，每次都是临时编一个陌生角色，模型二次元审美又弱，还总夹带乱码水印，要写脚本事后擦除。

这次彻底换了个思路：

  1. 把我自己收藏的 21 张 AI 人设图登记成「角色库」——11 个星座少女 + 4 个编程海报角色 + 5 个现成角色，每个角色配一份档案（发色、瞳色、服装、专属色板）
  2. 封面改用字节的 Seedream 5.0 生成，关键是它支持垫图：把角色原型图喂进去，生成的人物就真的是「同一个人」
  3. 角色按文章主题分配：MySQL 文章配水瓶座的冰蓝系，部署类配金牛座的暖棕系
项目 重构前 重构后
角色来源 文字临时编造 20 个固定角色垫图
单张生成 12~20 秒 + 事后擦水印 15 秒，直出可用
一致性 每次都是陌生人 同一角色一眼可辨

🧩 第三章：功能三件套——搜索、评论、统计

这三个属于「博客 eventually 都要装」的东西，这次一次配齐：

  • 本地搜索：hexo-generator-searchdb 生成全站索引，配合 Butterfly 的搜索弹窗，无需任何外部服务
  • 评论：选了 Giscus——用 GitHub Discussions 当评论后端，零成本零维护，评论数据就在自己仓库里
  • 统计：本想在自己服务器上装 Umami，结果 2核2G 的小服务器带不动 Umami + PostgreSQL 全家桶，果断改用官方云托管版（免费额度每月 10 万次访问，个人博客根本用不完）

🎨 第四章：主题换装——粉色系终于统一了

之前有个很别扭的点：站点背景是粉色，但主题的主色还是默认蓝，链接按钮全是蓝的，怎么看怎么违和。这次把主色整个换成玫红色系（#ff7c9c），链接、分页、滚动条、引用块全部统一。

暗色模式也顺手治了：原来夜间模式下粉色背景亮得刺眼，现在换成了暗玫瑰底色。

性能方面开了三件套：原生懒加载（首屏不再全量加载图片）、fancybox 灯箱（文章图片点击放大）、instantpage（悬停预加载）。还把主题的第三方资源全部本地化，不再依赖 jsdelivr——国内访问速度直接起飞。

🐳 第五章：看板娘换届——miku 下岗，鲸鱼娘上岗

原来的 Live2d miku 有个历史遗留问题：配置文件里写了三份互相矛盾的配置（模型不同、位置都不同），改哪份都「没反应」。这次直接一劳永逸——换成了 GitHub 上的开源项目 dsh-whale-musume（鲸鱼娘桌宠）。

这个项目原本是给另一个工具做的插件，我研究后发现它的核心（状态机 + 92 张立绘）对宿主零依赖，资源路径还正好匹配 Hexo 的部署结构——于是拷进项目、挂载两个 script，miku 光荣下岗。现在的看板娘会用视线跟着你的鼠标转，点击还有互动台词。

🚀 第六章：push 即发布——部署这件事自动化了

原来的发布流程：本地 hexo clean → hexo generate → hexo deploy，换个电脑还得重装全套环境。

现在配好了 GitHub Actions：源码推送到 source 分支，云端自动装环境、构建、把生成的页面推到 Pages 分支。发布流程变成了：

push 即发布，两分钟后全网可见。而且用的是 GitHub 内置的 token，连 Secret 都不用配置。

⚠️ 踩坑记录（本篇灵魂，全是真实伤口）

坑一：Seedream 5.0 不认 4.0 的参数。 生成接口里带了 sequential_image_generation（4.0 的组图参数），直接 400 报错。查了一圈才发现在 5.0 里这个参数被移除了。

坑二：版权过滤连自己的图都拦。 用「C# 推荐海报」里的角色当垫图，输出直接被 PolicyViolation 拒绝——大概率是画面里复现了品牌元素。换成原创星座角色就过了。结论：垫图素材尽量用无品牌元素干净的图。

坑三：AI 生成的文字必须逐张检查。 flash 模型 15 秒一张是快，但偶尔会写出「Ubunta」（Ubuntu）、「pppm」（pnpm）这种神奇拼写。12 张封面生成了两轮半才全部合格，自动化归自动化，人眼终检不能省。

坑四：角色锁不住，要在提示词里写小作文。 只说「保持角色一致」是不够的，金牛座的暖禾能被生成成天蝎座的样子。最后把角色档案里的外貌描述整段写进 prompt，才彻底稳定。

坑五：git push 假成功。 本机系统环境变量里残留了一个死代理地址，GitHub 直连不通，push 实际失败了，但命令管道把退出码吞了，显示一切正常。后来发现 git 的退出码要用 ${PIPESTATUS[0]} 取，或者干脆推送后用 GitHub API 验证。

坑六：nginx 报 invalid port in upstream。 给 Umami 配反向代理时，1Panel 生成的配置把 http://127.0.0.1:3000 塞进了只接受 host:port 的位置，nginx 把 http: 的冒号当成端口分隔符直接罢工。

坑七：2C2G 的服务器别硬塞数据库。 Umami + PostgreSQL 在我那台还跑着好几个容器的服务器上根本装不动。认清硬件边界，及时换云托管方案，不丢人。

📊 总结：重构前后对比

维度 重构前 重构后
图片总体积 33MB（单张封面 1.8MB） 15MB（单张 ≤300KB）
版本控制 ❌ 无 ✅ git 全程留痕
封面生成 文生图临时角色 + 擦水印 角色库垫图，15 秒直出
搜索/评论/统计 全没有 本地搜索 + Giscus + Umami
看板娘 三份打架的配置 一只鲸鱼娘
发布方式 本地三连命令 push 即发布
主题 粉底蓝链接 玫红统一 + 暗色适配

✅ 要点提炼：重构不是推倒重来，而是先体检、再扶正、后装修。最贵的不是技术，是「知道自己哪里烂」。

🌱 写在最后

这次重构让我最大的感受是：一个人 + AI，真的能干出一个小团队的活。扫描诊断、写脚本、生成图片、查资料、盯构建，我负责做决定和验收，AI 负责执行和排错，配合起来效率高得吓人。

当然也有没收尾的：文章分类现在还有 26 个（27 篇文章快一人一个了 😂），下一步计划收敛成 8 个大类、技术栈全部下沉到标签。革命尚未成功，小🐟仍需努力。

如果你也在养一个年久失修的博客，建议找个周末照着这个思路大修一次——修完那一刻的爽感，值得所有的坑。有问题欢迎在评论区留言，我们下一篇博客见！💬
